## 一、你有沒有遇過這種情況

你叫 AI 幫你做一件事，它做了一半、卡住、然後開始繞圈子，或者一直問你「這樣可以嗎？」，或者更慘的情況：跑了很久什麼結果都沒有，你也不知道它在哪個步驟出了問題。

這不只是 prompt 寫得不夠清楚的問題。更根本的原因是：**現在大多數 AI agent 的執行方式，本來就沒有設計「結束條件」、「失敗怎麼辦」、「跑完了要怎麼交代結果」**。

這就是「loop engineering」想解決的事。

如果你有在追 AI 社群，2026 年 6 月中旬你一定看過這個詞。它出現在 Substack、Medium、X，被說成是繼 prompt engineering（怎麼下指令）、harness engineering（怎麼搭建 agent 的執行環境）之後的下一個演進階段。簡單說就是：你不再只是給 AI 一句話，而是「設計整個讓 AI 反覆運作的循環」。

有兩篇 arXiv 論文，分別從不同角度給這件事建立了學術框架。一篇（Hassan et al., 2025）定義了什麼叫「好的 agent loop」；另一篇（Hu Wei, 2026）則直接解剖現在的 agent loop 哪裡有問題，並提出具體的解法。


## 二、第一個視角：讓 agent 的執行變得「有章可循」（Hassan et al., arXiv:2509.06216）

想像一間工廠。以前的做法是每天早上你跟工人說「今天去做 A、B、C」，工人自己想辦法。有沒有做完？你不確定。中間出了什麼問題？工人說不清楚。下次要重複一樣的流程？只能重新說一遍。

Hassan 等人在 2025 年 9 月的論文裡提出的框架，就是要把這間工廠改造成有 SOP 的生產線。他們把這件事叫做「**Agentic Loop Engineering（ALE）**」，核心目標是：讓 AI agent 的執行過程變成一種**可以被審查、可以被重現**的工作流程，而不是讓 agent 每次都在自己的記憶裡即興發揮。

他們設計了兩個配合運作的「工作台」：

**ACE（Agent Command Environment）**，也就是人類坐鎮的指揮中心。這裡負責管理整個 agent 團隊在做什麼、輸出結果長什麼樣、以及當 agent 遇到不確定的情況時，要怎麼回來問人。

**AEE（Agent Execution Environment）**，也就是 agent 實際去做事的空間。agent 在這裡執行任務，但如果遇到「我不確定該怎麼選」或「這個決定超出我的授權範圍」，它可以主動回到指揮中心請求人類介入，而不是自己亂猜。

這個論文最有趣的提案之一，是設計一套「**LoopScript 語言**」：一種宣告式的腳本，讓你能清楚寫出這個任務應該怎麼被分解、哪些步驟可以平行跑、哪些地方需要人工確認才能繼續。概念有點像你在寫 CI/CD 流程設定（`.yml` 那種），只是對象換成了 agent 的執行邏輯。

這篇論文本身是概念框架與研究藍圖，沒有提供可以直接跑的系統。但它的貢獻在於給了「loop engineering」一套共通的語言，讓研究者和工程師有辦法討論同一件事。

[ref: Hassan et al., arXiv:2509.06216, preprint, 尚未同儕審查]


## 三、第二個視角：現在的 agent loop 有三個根本問題（Hu Wei, arXiv:2604.11378）

如果 Hassan et al. 的工作是「定義好的 loop 應該長什麼樣」，Hu Wei 在 2026 年 4 月的論文則是從另一個方向切入：「你有沒有想過現在的 agent 為什麼這麼容易出錯？」

Hu Wei 把現在主流的 LLM agent 執行方式稱為「**Agent Loop**」。它的運作邏輯大概是這樣：agent 讀取一個不斷增長的「記憶清單」（context window），從裡面推斷出下一步要做什麼，然後做，然後再把結果加進記憶清單，再決定下下一步……不斷循環，直到它覺得完成了為止。

聽起來很合理，但這個設計有**三個根本的結構性弱點** [ref: Hu Wei, arXiv:2604.11378, preprint]：

**第一個弱點：沒有人知道步驟之間怎麼連在一起。**

哪個步驟依賴哪個步驟的結果？全部藏在 agent 的「記憶」裡。外面看不到、追蹤不了、也沒辦法驗證。就像你交給實習生一個任務，他沒有留下任何紀錄，你只能相信他記得該先做什麼、後做什麼。

**第二個弱點：失敗了不知道要停在哪裡。**

當 agent 某個步驟跑失敗，它通常的反應是：再試一次。再失敗，再試一次。這個循環可以跑多久？沒有明確限制。你可能回來看它，發現它還在重試同一件事，已經跑了一個小時。

**第三個弱點：執行紀錄會被自己改掉。**

這是最難被察覺的問題。因為 agent 的「記憶」是它每次執行的參考基礎，而這份記憶可以在過程中被改寫。出了問題你想事後重現？很難，因為 agent 在執行過程中已經把當時的狀態覆蓋掉了。

### 解法：把「隱藏在記憶裡的邏輯」搬出來，做成看得見的圖

Hu Wei 提出的解法叫做 **SGH（Structured Graph Harness）**。用白話說，就是：**把 agent 要做什麼、按什麼順序做、做失敗怎麼辦，全部事先寫清楚，做成一張圖，而不是讓 agent 在執行過程中自己決定。**

這張圖在技術上叫做「靜態有向無環圖（DAG）」，你可以把它理解成一張有方向箭頭的流程圖：每個節點是一個任務，每條箭頭說明「這個做完才能做那個」。整張圖在任務開始之前就確定好了，agent 執行過程中不能偷改。

SGH 給自己定了三個規則：
- **計畫一旦開始就不能改**：agent 不能在執行到一半時自行更新計畫，只能按照事先定好的圖走
- **規劃、執行、處理失敗，三件事分開做**：不要讓 agent 邊跑邊想邊修，各個環節各司其職
- **失敗有明確的升級流程**：跑失敗不是無限重試，而是走一個清楚的程序，例如先試一次備用方案，還是不行就交回給人類處理

這樣的設計犧牲了一些彈性（agent 不能臨機應變），但換來了可控性和可驗證性：你知道它在做什麼、它什麼時候會停下來、出了問題你找得到是哪個節點壞掉的。

Hu Wei 分析了 70 個已有的 agent 系統，建立了一套理論框架，說明 Agent Loop 和 SGH 這類圖結構執行引擎其實在同一個設計空間裡，只是在「靈活度 vs 可控性」這個軸線上站在不同位置。

需要說明的是，這篇論文是設計提案與理論框架，**本身不包含實驗數據或已部署的系統**。[ref: Hu Wei, arXiv:2604.11378, preprint]


## 四、兩篇放在一起看：問題是同一個，切入點不同

Hassan et al. 從「正面建設」出發，問的是「一個好的 agent 執行框架應該有哪些組成部分？人類和 agent 的分工應該怎麼設計？」

Hu Wei 從「問題診斷」出發，問的是「現有的做法哪裡不對？從工程學的角度怎麼修？」

兩篇放在一起，指向同一個結論：**你給 AI 的 prompt 寫得再好，如果底下跑著一個沒有終止條件、失敗了不知道怎麼辦、執行紀錄會消失的 loop，任務就是不可靠的。**

這也是為什麼「loop engineering」這個詞在 2026 年 6 月會突然出現。不是又一個新名詞在炒作，而是社群真的感受到：光是調整 prompt 和工具，已經不夠了。


## 五、對研究者的實際意涵

如果你在用 AI agent 協助研究流程（文獻整理、程式碼生成、資料分析），這個概念的意涵很具體：

**在你把任務丟給 agent 之前，先問自己三個問題：**

「怎麼知道它做完了？」如果沒有可以檢查的完成標準，agent 可能永遠在跑，也可能跑到一半就以為完成了。

「它做錯了怎麼辦？」如果你沒有設計失敗的處理流程，agent 的預設行為往往是繼續嘗試，而不是停下來告訴你出了什麼問題。

「它做了什麼，我之後還能重現嗎？」如果無法重現，出了問題你也找不到根源，更沒辦法改進。

這三個問題，就是 loop engineering 在實務上最直接的意義。不是技術術語，而是在使用 AI agent 之前，應該先想清楚的事。
